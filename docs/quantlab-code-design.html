1. 代码设计的第一原则

项目把“不确定的语言推理”和“必须正确的量化计算”拆开处理。LLM 不能直接做事实来源，也不能直接拥有系统执行权。

LLM：理解用户意图、规划下一步、解释工具结果 │ ▼ 程序：校验参数、执行工具、计算指标、写入文件、保存审计记录 │ ▼ 结果：只有经过工具与 Schema 校验的工件，才能成为研究证据
设计意义：“模型说 Sharpe 是 1.2”不是事实；只有回测脚本生成、Runner 校验并保存的 metrics.sharpe 才是系统认可的结果。

2. 分层架构：每层只做一类事情

CLI / React Web │ ▼ Service / FastAPI API ← 入口、权限、请求编排 │ ▼ Agent Kernel ← 有上限的 模型 → 工具 → 观察 循环 │ ▼ Tool Layer ← 研究、回测、文件、治理等确定性能力 │ ▼ Runtime / Workspace ← Projects、Runs、Events、Artifacts、Data Assets
层核心职责不应该承担的职责
UI / CLI收集任务、展示状态和证据计算指标、判断回测是否可信
Agent根据上下文挑选下一步工具直接读写任意文件、直接下单
Tool执行受控的确定性动作无限规划、绕过路径或 Schema 检查
Runtime保存项目、实验、事件和工件推理研究结论

3. Agent Kernel：quant_lab_agent/agent.py

Agent.__init__()

依赖注入，而不是硬编码

构造函数接收 llm、tools、workspace、审计日志和预算参数。

  • 便于用真实 OpenRouter 模型或离线 ScriptedLLM 替换；
  • 工具通过 by_name 建立白名单；
  • 测试时可以替换任意一个依赖。
Agent.chat()

有边界的主循环

每轮调用模型；若模型返回工具调用，则执行工具并把结果塞回消息列表；若没有工具调用，则返回最终文本。

  • max_rounds 防止无限循环；
  • 同一回测脚本有重跑预算；
  • 每轮写入 latency、token、tool call count。
_execute()

工具网关

所有工具调用都会经过同一个网关，而不是让模型直接调用函数。

  • 未知工具直接拒绝；
  • inspect.signature(...).bind() 校验参数；
  • 异常转换为可观察的错误文本，而不是让 Agent 进程崩溃。
_record_tool_event()

将执行变为证据

记录工具名、参数、结果、耗时，并从回测 JSON 中提取失败分类。

  • 写入 Audit Log；
  • 可选写入 RunStore；
  • 前端 Agent Trace 直接读取这些事件。
for round_number in range(1, max_rounds + 1):
    response = llm.chat(system + messages, tool_schemas)
    messages.append(response.message)

    if not response.tool_calls:
        return response.content

    for call in response.tool_calls:
        result = execute_and_validate(call)
        messages.append({"role": "tool", "content": result})

return "Stopped: maximum tool rounds reached"

4. 模型适配层：quant_lab_agent/llm.py

Agent Loop 不依赖 OpenAI SDK 的原始对象，而是依赖项目自己的 LLMResponse 和 ToolCall。

Provider boundary

LLM

使用 OpenAI-compatible SDK；可对接 OpenRouter 或 OpenAI。负责把供应商返回格式转成统一内部格式。

Offline test

ScriptedLLM

按预设 turn 返回结果。单测和评测不需要 API Key，也不会产生模型费用。

5. 工具系统：quant_lab_agent/tools/

base.py

工具协议

工具具有名称、描述、JSON Schema 与 execute()。模型只看 Schema，程序只调用允许的工具。

research.py

研究证据工具

登记假设、数据血缘、方法、复现命令和回测指标，把研究内容变为结构化记录。

backtest.py

受限回测 Runner

无 Shell 启动 Python；限制工作目录、脚本扩展名与超时；读取指定 JSON 结果文件。

governance.py

治理工具

检查缺失指标、风险阈值和人工审批状态。回测成功不等于允许部署。

workspace.py

文件边界工具

只允许在 workspace 内读取或基于唯一锚点做有限文本修复，避免任意文件访问。

__init__.py

工具装配

default_tools(workspace) 是能力白名单。给 Agent 哪些工具，就决定了它最多能做什么。

6. 回测 Runner 的代码设计

回测 Runner 是最需要谨慎设计的模块：它位于“LLM 想做什么”和“本机真的执行什么”之间。

路径解析
用 workspace-relative path 解析脚本与结果文件；工作目录以外的路径直接拒绝。
启动进程
使用 subprocess.run([sys.executable, "-I", script])，而不是拼接 Shell 字符串。
最小环境
只传递必要环境变量，默认不把完整宿主环境和 API Key 交给回测脚本。
验证新工件
先删除旧结果，避免旧文件被误判为本次成功；超时、退出码和缺失文件都有结构化失败。
Schema 校验
要求 sharpe、max_drawdown、turnover 为有限数字；曲线必须是日期/数字二元组。

7. Runtime：从一次聊天到可恢复实验

runtime/run_store.py

RunStore

一个 Run 对应一次实验。manifest.json 保存终态，events.jsonl 追加保存过程事件。

  • create() 创建 Run ID；
  • record_event() 追加事件；
  • finish() 写入最终状态；
  • annotate() 加入 project_id 等元数据。
runtime/project_store.py

ProjectStore

Project 与 Run 分离：Project 是研究主题，Run 是里面的一个实验。

  • 保存 thesis、universe、benchmark、owner；
  • 项目下可连续运行多个实验；
  • 解决“一问一报告”的产品结构问题。
audit.py / context.py

审计与上下文预算

审计日志记录完整过程；ContextManager 在上下文接近预算时压缩消息，减少长任务失控或成本增长。

service.py

应用服务

CLI 和 Web 共用的装配点：读取 Run → build_agent → chat → terminal_status → finish。

8. Web 与 Research OS 模型

React App.tsx ├── Overview：引导研究模板 ├── Research projects：项目、假设、股票池、实验数 ├── Runs：单次实验、图表、指标、Agent Trace ├── Data assets：本地上传与血缘 └── Governance：研究边界与复核状态 FastAPI api.py ├── /api/projects ├── /api/templates/run ├── /api/runs / events / backtest └── /api/data-assets

前端不自己计算金融指标；它只请求后端保存过的 Run 与 Artifact。这样网页刷新、换浏览器或之后复核时，研究证据仍在本地工作区。

9. 一次“项目内实验”的完整代码流

① 创建项目
React 调用 POST /api/projects → ProjectStore.create() 写入本地项目注册表。
② 启动模板实验
React 调用 POST /api/templates/run → RunStore.create() 创建 Run，并用 annotate(project_id=...) 与项目关联。
③ 写入研究协议与数据来源
后端将 Hypothesis、Data validation、Baseline 等阶段写成事件；演示数据也被明确写入 warning。
④ 执行确定性脚本
后端通过 RunBacktestTool 调用受控的模板回测脚本，生成 JSON Artifact。
⑤ 校验与完成
Runner 校验指标和曲线 → 记录 tool_call → 保存 template report → RunStore.finish() 写最终状态。
⑥ 前端展示
Runs 页读取 events 与 backtest，展示曲线、指标、比较卡片和 Agent Trace。

10. 最复杂的真实开发问题与现有边界

问题当前设计如何处理生产级下一步
Agent 无限修复/重跑最大轮次 + 每脚本重试预算 + needs_review队列级重试策略、幂等任务和人工介入队列
模型编造指标只有 Runner 校验的 JSON 才是证据工件签名、数据版本快照、独立验证 Worker
不可信策略代码无 Shell、workspace 边界、超时、最小环境容器/Firecracker、无网络、只读挂载、资源限额
真实市场数据质量上传文件 Hash 与数据来源事件复权/拆股、缺失值、幸存者偏差、供应商版本治理
多实验可比较性Project → Run 关联与模板化协议参数矩阵、基准快照、实验版本和统计显著性检验

最新运行时能力：真实数据、受控策略与预测情景

CODE UPDATE · 2026-08-27

最新代码增加 fetch_us_market_data、create_strategy_template 与 forecast_market_direction。用户可输入 英伟达、NVIDIA 或 NVDA；LLM 决定下一步，但固定工具负责名称解析、市场数据快照、数据校验、策略编译、回测和预测诊断。

自然语言任务→ 行情快照→ 数据校验→ 策略 / 预测→ 受限计算→ 证据/治理
  • tools/market_data.py：经固定 Alpha Vantage 适配器获取 OHLCV，校验日期、必填字段、重复日期、价格高低关系和成交量；保存 CSV、lineage JSON、SHA-256。Key 不进入 LLM 上下文。
  • tools/strategy_template.py：只允许 buy_and_hold、moving_average、mean_reversion 三种策略；校验窗口、z-score、成本和 CSV 列后，生成可审阅的策略规格与标准库脚本。
  • tools/forecast.py：使用可解释的 AR(1) 历史收益率情景模型，输出上涨概率、统计区间，以及滚动样本外方向准确率和 Brier score；预测 Artifact 含数据 SHA-256 与限制说明。
  • 策略脚本保存到 backtests/generated/，规则保存到 .quant-agent/strategy-specs/，回测和预测结果保存到 artifacts/；run_backtest 仍负责无 Shell 执行、超时、JSON Schema 与 SHA-256 校验。
“分析近三年走势”不等于策略回测或预测。“上涨概率”只是历史模型产生的统计情景，不是必然价格、买卖建议或自动交易依据。复权、幸存者偏差、流动性和样本外验证仍需额外研究。

结论：QuantLab 的代码核心不是“调用一次 LLM”，而是把 LLM 放进一个有工具白名单、执行边界、结果验证、状态持久化和治理终态的研究系统中。
