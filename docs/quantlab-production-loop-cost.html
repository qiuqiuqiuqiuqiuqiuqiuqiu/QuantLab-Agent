循环与成本控制的生产级设计

本页基于最新代码说明：任务如何在调用模型之前、调用模型之后、调用工具时分别控制成本和循环；并用真实生产事故说明还需要哪些升级。

1. 先给结论

Agent 的成本控制不能只靠 max_rounds=30。当前版本使用了调用前 Token 预检 + 调用后真实 Token 记账 + 回测重跑预算 + 只读工具缓存 + 上下文压缩 + 完整运行摘要的组合控制。

2. 当前一次 Agent Run 的实际控制流

创建 Run
  │
  ├─ 每一轮开始：压缩上下文（必要时记录 context_compacted）
  │
  ├─ 预估下一次调用所需 Token：
  │      已用 Token + 预计输入 + max_completion_tokens
  │
  ├─ 若超过 max_total_tokens：在调用模型前停止
  │
  ├─ 调用 LLM：对 429 / timeout / 5xx 做有限退避重试
  │
  ├─ 记录真实 prompt / completion Token 与估算美元成本
  │
  ├─ 若真实用量超过预算：停止后续工具调用
  │
  ├─ 执行工具：回测有单脚本重跑预算；只读工具可命中缓存
  │
  └─ 完成、预算停止或轮次停止：写入 agent_summary

3. 代码中已有的六道护栏

01 · ROUND CAP

最大循环次数

max_rounds 默认 30。防止模型不断进行“模型 → 工具 → 模型”的循环。

02 · PREFLIGHT

调用前 Token 预检

调用前估算 system prompt、消息历史与最大输出预留；若剩余预算不够，不再发起昂贵调用。

03 · ACTUAL USAGE

调用后真实记账

累计 provider 返回的 prompt / completion Token；即使预估偏低，也会阻止继续调用工具或下一轮。

04 · RETRY BUDGET

回测重跑限制

同一个脚本仅允许首次运行加有限修复重跑，超过后转人工复核。

05 · TOOL CACHE

只读工具缓存

纯只读工具使用“工具名 + 规范化参数”指纹；同一 Run 中重复读取同一文件可直接返回缓存结果。

06 · OBSERVABILITY

运行摘要与压缩事件

保存总轮数、总 Token、估算成本、终止原因与上下文压缩事件，便于复盘。

4. 最大循环次数如何确认？

30 是默认的工程护栏，不是一个放之四海皆准的数字。它应从“正常成功路径需要几轮”与“异常路径最多允许浪费几轮”两个方向确定。

任务正常路径示例建议 max_rounds
读取已有实验读取记录 → 总结5
单股研究登记 → 数据检查 → 计算 → 治理 → 结论10–15
策略回测登记 → 读脚本 → 回测 → 一次修复 → 再回测 → 验证15–20
复杂多资产实验多个数据/工具步骤，仍应避免同步长任务25–30
大规模参数扫描不应该继续占用 Agent 同步循环改任务队列 / Worker

在 QuantLab 中，最大轮数从不单独发挥作用；它与 Token 预算、回测重跑预算和工具超时共同形成多层边界。

5. 当前代码的关键实现

A · BEFORE CALL

预检预算

当前实现estimate_tokens(system + messages) 估算下一次输入，再加上 max_completion_tokens 作为输出预留。若 already_spent + predicted_input + reserve > max_total_tokens，直接停止。
解决的真实场景某任务已用 36,000 Token，当前消息历史估算 3,500 Token，而模型最大输出为 4,096 Token。若总预算为 40,000，继续调用极大概率超预算。现在系统会在发送请求前停止，而不是等产生账单后才发现超支。
B · AFTER CALL

真实用量与成本

当前实现从模型响应中累加实际 prompt_tokens 和 completion_tokens；按环境变量配置的每百万 Token 输入/输出价格计算 estimated_cost_usd，写入 llm_response 和 agent_summary。
解决的真实场景提供商的真实 tokenizer 与本地粗略估计不同，或模型返回比预留更长的输出。调用后检查确保系统不会继续开始昂贵的工具和下一轮。
C · TOOL PHASE

减少无价值操作

当前实现只读工具有 cacheable=True 标记。Agent 为工具调用构造稳定指纹，命中后写入 cache_hit=true，不重复执行。回测则按 script_path 计数，避免重复修复。
解决的真实场景模型在第 3、6、8 轮反复要求读取同一个脚本，只是因为没有正确利用上文。缓存可以减少文件 I/O 和工具事件；回测预算则防止 CPU 密集的无意义重跑。
D · LONG CONTEXT

上下文压缩

当前实现ContextManager 先裁剪超长工具输出，再压缩旧历史，最后仅保留近期消息。发生压缩时记录 context_compacted。
解决的真实场景回测 traceback 或 CSV 摘要过长。若原样放进后续每次模型请求，费用会不断放大；分层压缩保留近期决策所需内容。

6. 真实生产里仍会发生什么？如何进一步解决？

真实事故当前代码能做什么生产级补强
100 个用户同时启动研究，单 Run 都没超预算，但团队一天花费超标。提供单 Run Token 与估算成本记录。在数据库中实现 user / project / workspace 三层原子预算预留；队列提交前扣减，完成后按真实 usage 结算。
OpenRouter 连续 429，所有任务同时指数重试，形成重试风暴。单调用有限退避重试。供应商级熔断器、全局并发限制、Retry-After 遵从、排队与退避协调。
同一只读文件在工具缓存后被另一个步骤修改，缓存结果变旧。当前只对明确标记为只读的工具缓存，范围仅限一个 Run。缓存键加入文件 SHA256 / mtime；发生写入时失效对应路径缓存。
模型不断调用不同参数的“相似回测”，绕过同脚本重跑计数。当前按 script path 限制重跑。增加实验级预算：限制回测次数、CPU 秒数、参数空间大小；参数扫描交给专用 Worker。
估算美元价格表过期，成本记录不准确。价格通过环境变量显式配置，记录为 estimated。版本化模型价格表、供应商账单对账、货币预算使用保守预留而非只依赖估算。
一个回测脚本卡在 CPU 密集计算，Agent Token 控制正常但机器资源被耗尽。Runner 有超时。隔离容器、CPU/内存/PID 限制、任务队列、取消信号和每项目资源配额。

7. 生产配置示例

QUANT_AGENT_MAX_ROUNDS=20
QUANT_AGENT_MAX_BACKTEST_RETRIES=2
QUANT_AGENT_MAX_TOTAL_TOKENS=30000
QUANT_AGENT_MAX_TOKENS=2048
QUANT_AGENT_LLM_MAX_RETRIES=3

# 用于本地“估算成本”，不是供应商账单真值
QUANT_AGENT_INPUT_COST_PER_MILLION=2.50
QUANT_AGENT_OUTPUT_COST_PER_MILLION=10.00
注意：当前已实现的是可靠的单 Run 生产基线，而不是完整多租户成本平台。全局并发、用户/项目美元配额、容器隔离和账单对账需要在 Worker、队列和数据库层继续实现。

自然语言任务→ 行情快照→ 数据校验→ 策略 / 预测→ 受限计算→ 证据/治理
