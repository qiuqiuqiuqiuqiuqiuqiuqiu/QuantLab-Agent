UPDATED · ENGINEERING DEEP DIVE

QuantLab Agent
核心价值、工程难点与最新改进

基于当前代码版本整理：包含项目/实验模型、受限回测、Token 预算、模型重试、Artifact 哈希和完整 Agent 运行摘要。

项目最重点的部分：不是生成股票观点，而是建立一个受控的研究执行闭环：LLM 规划下一步，确定性工具产生事实，Runtime 保存证据，治理规则决定何时停止或交给人工。

1. 当前版本的四个核心能力

01 · CONTROL

有预算的 Agent 控制

最大轮次、同脚本回测重试预算、总 Token 预算。模型不能无限思考或无限重跑。

02 · RELIABILITY

可靠模型调用

对超时、限流和 5xx 等临时供应商错误进行指数退避重试；认证和配置错误立即暴露。

03 · EVIDENCE

可验证研究工件

回测指标来自受限 Python Runner；JSON Schema 校验通过后，额外记录 Artifact SHA256。

04 · TRACEABILITY

完整运行可观测性

保存项目、实验、数据血缘、工具调用、上下文压缩、Token 汇总与最终停止原因。

2. 最复杂的真实开发问题

难点不在于写一个 while 循环，而是让这个循环在接触真实模型、真实数据、真实脚本和真实成本后，依然可以限制、检查、追踪和停止。

工程目标是：给 Agent 足够的行动能力，同时保证每次行动都可限制、可验证、可追溯、可停止。
CHALLENGE 01

循环与成本失控

会遇到的问题模型可能反复读脚本、修改、回测、再修改；长任务还可能持续积累上下文和 Token，最后既没有结果也没有成本边界。
当前代码如何解决
  • max_rounds 控制 Agent 最大轮次；
  • max_backtest_retries 控制同一 script_path 的修复/重跑预算；
  • max_total_tokens 累计每轮 prompt 与 completion Token；超过预算时返回 token_budget 停止；
  • 写入 agent_summary：总轮数、输入/输出 Token、总 Token 和结束原因。
生产级下一步任务队列、组织级美元预算、取消信号、幂等键和人工升级队列。
CHALLENGE 02

模型供应商不稳定

会遇到的问题OpenRouter 或模型 API 可能出现 429、网络超时或暂时性 5xx。简单地失败会损伤体验；无差别重试则会放大问题或掩盖认证错误。
当前代码如何解决
  • LLM.chat() 识别 408、409、429、500、502、503、504 和网络连接错误；
  • 使用指数退避与随机抖动；
  • 由 QUANT_AGENT_LLM_MAX_RETRIES 配置上限，默认 3 次；
  • 鉴权和配置错误不重试，立即返回给用户。
生产级下一步备用模型链路、熔断器、供应商级成功率监控和真实货币成本记账。
CHALLENGE 03

数值幻觉与旧结果误用

会遇到的问题LLM 可以写出看似专业的 Sharpe 和回撤；脚本也可能没有生成新结果，却误把上次的旧 JSON 当成本次成功。
当前代码如何解决
  • LLM 不直接计算或登记正式量化指标；
  • Runner 先删除已有 result 文件，再执行指定脚本；
  • 要求 sharpe、max_drawdown、turnover 为合法有限数值；
  • 成功 Artifact 会记录 artifact_sha256，让指标和具体 JSON 文件建立内容级关联；
  • 无成功 Artifact 时，研究状态不能称为已验证。
生产级下一步数据快照哈希、结果签名、独立验证 Worker 和报告引用完整性检查。
CHALLENGE 04

Agent 执行代码的安全性

会遇到的问题Agent 若能任意运行代码，可能读取密钥、访问目录外文件、联网装包、无限运行或覆盖错误数据。
当前代码如何解决
  • 通过参数数组启动 Python，不拼接 Shell；
  • 只允许 workspace 内的 .py 脚本和结果路径；
  • 有超时限制和最小环境变量；
  • 文件读取/修改工具也受 workspace 路径约束；
  • 未知工具与不匹配参数会被 Agent 网关拒绝。
生产级下一步Docker/Firecracker 一次性 Worker、无网络、只读数据挂载、CPU/内存/PID 限制。当前本地 Runner 不是完整安全沙箱。
CHALLENGE 05

上下文太长、审计不完整

会遇到的问题研究任务可能经过很多轮工具调用；完整工具输出全部塞进模型上下文会变贵且容易超窗口，但过度裁剪又会让模型丢失关键事实。
当前代码如何解决
  • ContextManager 使用三段式策略：先裁剪过长工具输出，再压缩旧历史，最后仅保留近期消息；
  • 每次压缩都会记录 context_compacted 事件及估算 Token；
  • 每轮保存模型耗时、Token、工具调用次数；
  • 最终保存 agent_summary，让一次运行可以从成本与执行结果两方面复盘。
生产级下一步持久化可恢复摘要、关键事实索引、按需检索和更精确的 provider tokenizer 计数。
CHALLENGE 06

从报告生成器到研究系统

会遇到的问题“输入一个问题 → 输出一个报告”无法沉淀同一主题的股票池、基准和多次实验，也无法实现后续实验矩阵和公平比较。
当前代码如何解决
  • ProjectStore 保存研究 thesis、universe、benchmark 与 owner；
  • RunStore 保存每次实验及其事件；
  • Run 通过 project_id 关联到研究项目；
  • 模板写入 research_protocol：Hypothesis → Data validation → Baseline → Robustness → Governance；
  • Data Asset 上传保存 SHA256、大小、时间和关联 Run。
生产级下一步参数矩阵、真实数据适配器、复权/公司行为处理、实验比较、统计显著性和项目级报告版本管理。

4. 面试时最值得强调的回答

我没有把 QuantLab 做成一个会给股票建议的聊天机器人。它的核心是一个受控 Agent Runtime：LLM 只负责规划与解释；Python 工具负责计算与执行；Runtime 负责项目、实验、证据和恢复；治理层负责限制与终止。

我针对真实 Agent 系统的四类问题做了工程约束：Token/轮次预算避免失控，临时错误重试提高供应商可用性，Artifact 哈希和 JSON Schema 防止结果幻觉，事件摘要与上下文压缩保证长任务可观测。生产环境下一步是把 Runner 迁移到隔离 Worker，并接入真实且版本化的市场数据。

最新运行时能力：真实数据、受控策略与预测情景

CODE UPDATE · 2026-08-27

最新代码增加 fetch_us_market_data、create_strategy_template 与 forecast_market_direction。用户可输入 英伟达、NVIDIA 或 NVDA；LLM 决定下一步，但固定工具负责名称解析、市场数据快照、数据校验、策略编译、回测和预测诊断。

自然语言任务→ 行情快照→ 数据校验→ 策略 / 预测→ 受限计算→ 证据/治理
  • tools/market_data.py：经固定 Alpha Vantage 适配器获取 OHLCV，校验日期、必填字段、重复日期、价格高低关系和成交量；保存 CSV、lineage JSON、SHA-256。Key 不进入 LLM 上下文。
  • tools/strategy_template.py：只允许 buy_and_hold、moving_average、mean_reversion 三种策略；校验窗口、z-score、成本和 CSV 列后，生成可审阅的策略规格与标准库脚本。
  • tools/forecast.py：使用可解释的 AR(1) 历史收益率情景模型，输出上涨概率、统计区间，以及滚动样本外方向准确率和 Brier score；预测 Artifact 含数据 SHA-256 与限制说明。
  • 策略脚本保存到 backtests/generated/，规则保存到 .quant-agent/strategy-specs/，回测和预测结果保存到 artifacts/；run_backtest 仍负责无 Shell 执行、超时、JSON Schema 与 SHA-256 校验。
“分析近三年走势”不等于策略回测或预测。“上涨概率”只是历史模型产生的统计情景，不是必然价格、买卖建议或自动交易依据。复权、幸存者偏差、流动性和样本外验证仍需额外研究。
