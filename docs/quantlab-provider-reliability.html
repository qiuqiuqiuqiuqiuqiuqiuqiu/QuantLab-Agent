模型供应商不稳定：问题与解决方案

LLM 供应商不是一个永远成功的函数调用。网络、限流、账户额度、模型发布、流量高峰和返回格式变化，都会让 Agent 在中间步骤失败。这个页面说明如何区分、重试、停止和升级问题。

1. 什么叫“模型供应商不稳定”？

QuantLab 通过 OpenAI-compatible API 连接 OpenRouter 或其他模型服务。一次 llm.chat() 调用要经过本地网络、DNS、HTTPS、供应商网关、路由平台、上游模型和计费系统；其中任一环节暂时或永久失败，Agent 都可能拿不到下一步工具决策。

QuantLab Agent │ ▼ OpenAI-compatible SDK │ ▼ OpenRouter / Provider Gateway ──→ quota / rate-limit / routing │ ▼ Upstream model provider ────────→ model availability / overload │ ▼ Response or error

2. 先分清：能重试的错误和不能重试的错误

TRANSIENT

暂时性错误

稍等后可能恢复：网络波动、请求超时、服务器短暂过载、短期限流。

TERMINAL

终态配置/账单错误

重试不会恢复：API Key 错误、余额不足、套餐不支持、权限不足。

AMBIGUOUS

429 是模糊错误

它可能代表“请求太快”，也可能代表“账户已无额度”；必须结合错误正文分类。

3. 真实开发中最常见的情况

CASE 01

请求超时 / 网络抖动

真实情况用户提交研究后，网络临时断开，或上游模型在 30 秒内没有响应。SDK 可能抛出 TimeoutError、连接错误，或者 HTTP 408。
当前代码处理llm.py 将 TimeoutError、ConnectionError 和 408 视为临时错误，最多按 QUANT_AGENT_LLM_MAX_RETRIES 重试。
生产进一步处理设置连接、读取和总请求超时；记录供应商延迟；当某地区网络长期不稳定时切换网关或区域。
CASE 02

429：请求太快

真实情况研究团队上午同时启动几十个 Run。平台限制每分钟请求数或 Token 数，后续请求返回 429 Too Many Requests。
当前代码处理429 在不含终态账单标记时被认为可重试：等待约 0.5 秒、1 秒、2 秒……并加少量随机抖动，避免所有任务同一时刻再次发送。
生产进一步处理遵从响应头的 Retry-After；实行全局并发阈值和令牌桶限流；把超额请求排队，不让每个 Agent 独立盲目重试。
CASE 03

429：账户额度不足

真实情况错误虽然也是 429，但正文包含 insufficient_quota，代表余额、套餐或项目额度已耗尽。等待十分钟也不会恢复。
当前代码处理最新 llm.py 会检查异常正文、code 与 type。若包含 insufficient_quota、billing、payment_required、invalid_api_key 或 authentication，会跳过重试，直接将错误交给上层 Run，避免无意义等待。
生产进一步处理将任务状态标为 provider_action_required；前端明确显示“需要充值/更换 Key/联系管理员”，并告警给管理员。
CASE 04

5xx：模型或网关过载

真实情况市场开盘、热门模型发布或供应商故障时，网关可能返回 500、502、503、504。任务本身没有错，但模型当前不可用。
当前代码处理这些 5xx 被判定为临时错误，使用有限的指数退避重试。达到上限后抛出异常，由 Service 将 Run 写为失败状态并保留原因。
生产进一步处理加入熔断器：连续失败后短时间不再访问该供应商；配置 fallback model / fallback provider；通过健康检查恢复流量。
CASE 05

返回格式或工具调用不兼容

真实情况某模型不支持 tool calling、返回不合法 JSON 参数，或模型升级后响应字段变化。调用成功但 Agent 无法解析，体验上等同失败。
当前代码处理llm.py 将响应转换为内部 LLMResponse/ToolCall；Agent 继续用函数签名验证工具参数，非法参数不会直接执行。
生产进一步处理做供应商兼容性测试集、模型能力注册表、JSON 解析错误分类、降级为纯文本澄清，以及版本锁定和灰度发布。

4. 当前重试算法如何工作？

for attempt in range(max_retries + 1):
    try:
        return provider_call()
    except error:
        if error is terminal:       # quota / billing / authentication
            raise immediately
        if error is transient and retry budget remains:
            sleep(0.5 × 2^attempt + random_jitter)
            retry
        raise

随机抖动（jitter）的作用是防止 100 个请求在整整 1 秒后同时重试，造成第二波 429；指数退避的作用是让系统在持续故障时逐步降低压力。

5. 为什么“自动重试”也会带来风险？

风险错误做法正确方向
重试风暴每个 Agent 收到 429 后立刻重试指数退避、jitter、全局限流、队列
隐藏账单问题所有 429 都重试解析 insufficient_quota，立即提示用户处理
重复执行网络超时后直接重发有副作用的工具区分 LLM 请求和工具请求；工具使用幂等键和事件日志
无限降级失败后无限切模型定义 fallback 链最大长度、能力要求、预算与审计
用户无感等待后台静默重试数分钟实时显示“正在重试 / 等待供应商恢复”，允许取消

7. 面试时如何总结

模型供应商不稳定不能只靠 try/except。关键是先区分“等一会儿会恢复”的故障和“用户必须处理”的故障。QuantLab 对 timeout、临时 429 和 5xx 做有限退避重试；对 insufficient_quota、账单和认证错误不重试，避免掩盖问题。生产环境还要增加集中限流、熔断器、备用模型和供应商观测指标。
